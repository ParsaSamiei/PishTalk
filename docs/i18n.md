# Bilingual (Persian / English) support

The site ships in Persian by default and can switch to English from the
segmented slider next to the theme toggle in the navbar.

## How the locale is chosen

The active locale lives in a **cookie** (`locale`, one year), not in the URL.
Every URL serves both languages — `/about` renders Persian or English
depending on the visitor's cookie.

Resolution order, in `lib/i18n/server.ts`:

1. The `locale` cookie, if set — an explicit choice always wins.
2. Otherwise Persian.

`Accept-Language` is deliberately **not** consulted. It used to be (parsed
with q-values, to land English speakers in English on their first visit), but
that meant an English-configured browser never saw the Persian site at all.
Persian is now unconditional until the visitor chooses otherwise, and that
choice then persists in the cookie.

The trade-offs of the cookie approach, so nobody rediscovers them the hard way:

- **No per-locale SEO.** Google indexes one version of each URL. If English
  search traffic ever matters, this is the thing to change.
- **English links aren't shareable.** Sending `/about` to an English speaker
  shows them Persian unless they flip the toggle themselves.
- **Pages can't be statically cached per locale.** Reading a cookie opts a
  route into dynamic rendering.

Moving to `/en/*` prefixes later means introducing an `app/[locale]/` segment
and a locale-aware `Link` helper. Everything else here — dictionaries,
`pick()`, the direction handling — carries over unchanged.

## Layout

```
lib/i18n/
  config.ts          locales, cookie name, direction and lang maps
  server.ts          getLocale / getDictionary / getLocaleContext  (Server Components)
  client.tsx         LocaleProvider, useLocale, useDictionary       (Client Components)
  actions.ts         setLocaleAction — the server action the toggle calls
  content.ts         pick() — English DB column with Persian fallback
  dictionaries/
    fa.ts            Persian — the canonical key shape
    en.ts            English — typed against fa.ts
    types.ts         derives the Dictionary type from fa.ts
    index.ts         getDictionaryFor(locale)
```

## Using it

**Server Component:**

```tsx
import { getDictionary } from "@/lib/i18n/server";

export default async function Page() {
  const d = await getDictionary();
  return <h1>{d.about.pageHeading}</h1>;
}
```

**Client Component:**

```tsx
"use client";
import { useDictionary } from "@/lib/i18n/client";

function Widget() {
  const d = useDictionary();
  return <button>{d.common.share}</button>;
}
```

`useOptionalLocale()` is the variant that falls back to Persian outside the
provider — needed in `app/global-error.tsx`, which renders above it.

### Adding a string

Add the key to `fa.ts` first. `en.ts` is typed as `Dictionary` (derived from
`fa.ts`), so the build fails until the English value exists too. That's the
point: a missing translation is a compile error, not a silent Persian
fallback in production.

## Database content

Translatable columns come in pairs: the Persian column and a nullable
`<field>En` sibling (`title` / `titleEn`). `pick()` returns English when it's
present and non-blank, and Persian otherwise:

```tsx
import { getLocaleContext } from "@/lib/i18n/server";
import { pick } from "@/lib/i18n/content";

const { locale } = await getLocaleContext();
const title = pick(locale, event.title, event.titleEn);
```

Content stays **Persian-first**: every English column is optional, so admins
can translate incrementally and an untranslated post still renders correctly
for an English visitor (in Persian). Nothing needs backfilling.

Admin forms show an English field beside each Persian one, labelled as
optional.

## Direction

`dir` on `<html>` follows the locale, and the layout is built on CSS logical
properties (`ps-`/`pe-`/`ms-`/`me-`/`start-`/`end-`/`text-start`), so it
mirrors without per-locale overrides. **Use logical utilities, not `pl-`/
`ml-`/`left-`** — physical ones don't flip and will look wrong in one of the
two languages.

Two things that don't mirror automatically:

- **Directional icons.** An arrow meaning "next" points left in Persian and
  right in English. Use `ForwardArrow` / `BackArrow` / `ForwardChevron` /
  `BackChevron` from `components/shared/DirectionalIcon.tsx` rather than
  importing `ArrowLeft` directly.
- **Carousels and arrow keys.** Embla takes an explicit `direction`, and
  ArrowLeft means "next" only in RTL. `GalleryLightbox` handles both.

Latin-only values (phone numbers, email addresses) keep `dir="ltr"` in both
locales — that's correct, not a leftover.

## Dates

`formatEventDate(date, locale)` and `formatWeekday(date, locale)` pick the
calendar from the locale: **Jalali** for Persian (`۱۴ خرداد ۱۴۰۴`),
**Gregorian** for English (`4 June 2025`). The `locale` argument defaults to
Persian, which is what the admin panel relies on.

## Scope

Translated: the whole public site — pages, navigation, forms, validation
messages, error and empty states, and SEO metadata.

Not translated: the **admin dashboard**, which stays Persian by decision. Its
forms gained English *input fields* so admins can enter English content, but
the dashboard's own labels and chrome are Persian.
